# FLOWGIC: Мастер-спецификация архитектуры и план трансформации (для ИИ-агента)

## 1. Контекст и цель проекта
**Flowgic** — облачная B2B SaaS-платформа (мини-CRM / TMS) для автоматизации малых и средних логистических компаний и производственных предприятий.
**Главная задача трансформации:** Перевести существующий монолитный прототип на Django Templates + SQLite (папка `src/`) на масштабируемую Headless-архитектуру в формате **Модульного Монолита (Modular Monolith)** с единым монорепозиторием, сохранив 100% существующей доменной логики моделей и тестового покрытия (`pytest`).

---

## 2. Целевой технологический стек
* **Репозиторий и CI/CD:** Единый Monorepo на GitHub + пайплайны GitHub Actions (`.github/workflows/`).
* **Backend Core:** Python 3.11 / Django 5.2 + **Django Ninja** (REST API на базе Pydantic) + **django-ninja-jwt** (единая JWT-авторизация).
* **База данных:** **PostgreSQL 16 + PostGIS** (геоданные маршрутов и координат). Полный отказ от `db.sqlite3`.
* **Кэш, очереди и Realtime:** **Redis** + **Celery** (фоновые задачи, уведомления, проверка лимитов) + **Django Channels** (WebSockets для обновления статусов и карты в реальном времени).
* **Frontend (Web — панель диспетчера, менеджера, бухгалтера):** **React (Vite + TypeScript)** + **Ant Design (AntD)** + **TanStack Query (React Query)** + автогенерация типизированного клиента из OpenAPI-схемы Django Ninja (`@hey-api/openapi-ts`).
* **Mobile (Приложение водителя):** **Flutter** (архитектура Feature-First, стейт-менеджер `Riverpod`, HTTP-клиент `Dio`, оффлайн-кэш `Drift`/`Isar`, автогенерация моделей из `openapi.json`).
* **Быстрые каналы и утилиты:** Telegram-бот для водителей (`aiogram` поверх REST API) и генератор печатных документов (Договор-заявка, ТТН) через `docxtpl`.

Строгие архитектурные правила для Бэкенда (Законы для ИИ-агента)
4.1. Трехслойная архитектура внутри каждого модуляЗапрещается писать бизнес-логику и сложные ORM-запросы внутри api.py или views.py. Каждый модуль (accounts, logistics, billing, marketplace, telemetry) обязан иметь следующую структуру:models.py — только описание таблиц БД, простых свойств и констант (сохранить текущие модели из src/accounts/models.py и src/logistics/models.py).schemas.py — входные (In) и выходные (Out) схемы Pydantic / ModelSchema из Django Ninja (полная замена старых forms.py).selectors.py — чистые функции только для чтения данных из БД (get_company_orders, get_vehicle_list). Обязаны использовать select_related / prefetch_related для предотвращения проблемы N+1.services.py — функции только для записи и бизнес-логики (create_order, update_order_status, calculate_order_profit). Все изменения нескольких таблиц оборачиваются в @transaction.atomic.api.py — тонкие роутеры Django Ninja. Задача эндпоинта: принять запрос -> проверить права и лимиты -> вызвать функцию из services.py или selectors.py -> вернуть типизированный ответ.tasks.py — асинхронные задачи Celery (отправка email/push, генерация тяжелых отчетов).
4.2. Границы модулей (Modular Monolith Rules)Модули не должны напрямую модифицировать модели чужих модулей через ORM.Если модулю logistics при создании заказа нужно проверить тарифный лимит, он вызывает публичный сервис billing.services.check_company_order_limit(company).
4.3. Жесткая Мультитенантность (Multi-Tenancy & RBAC)Каждый пользователь привязан к компании (user.company) и имеет роль (dispatcher, manager, driver).Абсолютное правило безопасности: Ни один запрос в selectors.py или services.py к таблицам Order, Client, Vehicle, Financial, OrderEvent не может выполняться без явной фильтрации .filter(company=user.company).Все изменения должны проходить проверку существующими тестами изоляции (test_data_isolation.py).
5. Архитектура бизнес-модели и монетизацииВместо баннерных сетей в архитектуру закладываются два механизма монетизации:
5.1. Модуль billing (Freemium + Тарифы от размера автопарка)Модели: SubscriptionPlan и CompanySubscription.Параметры тарифного плана компании:plan_type: FREE (бесплатный стартовый), PRO (оплата за активные ТС и пользователей), ENTERPRISE.max_vehicles: лимит машин (например, до 3 ТС на FREE).max_orders_per_month: лимит заказов в месяц (например, до 30 заказов на FREE).iot_enabled: доступ к телеметрии датчиков рефрижераторов (bool).Механика проверки через Redis: Счетчики активных ТС и заказов за текущий месяц кэшируются в Redis. При превышении лимита в services.py выбрасывается кастомное исключение QuotaExceededError, которое api.py преобразует в HTTP 402 Payment Required с понятным JSON-описанием для показа окна апсейла в React.
5.2. Модуль marketplace (Встроенные B2B-партнерки)Модели: PartnerOffer (категория: INSURANCE — страхование груза, FUEL — топливные карты, FACTORING — закрытие кассовых разрывов, TELEMATICS — установка ГЛОНАСС/датчиков) и OfferClickLog (лог кликов компании для биллинга лидов).Селектор get_contextual_offers(company, context_type, order=None) возвращает нативные предложения в интерфейс диспетчера (например, предложение застраховать груз в карточке дорогого заказа или подключить факторинг при наличии неоплаченных счетов в Financial).
6. Пошаговый план работ для ИИ-агента (Roadmap исполнения)Агент должен выполнять трансформацию строго последовательно, проверяя каждый этап тестами:
Этап 1: Очистка репозитория и контейнеризацияОчистить индекс Git от venv/, .pytest_cache/, __pycache__/ и src/db.sqlite3. Настроить .gitignore и .aiignore.   Переименовать src/ в backend/.Создать docker-compose.yml с сервисами db (postgis/postgis:16-3.4), redis (redis:7-alpine), backend и celery.Перевести settings.py на использование PostgreSQL и Redis через переменные окружения (.env).   Запустить pytest и убедиться, что все существующие тесты моделей и изоляции проходят на PostgreSQL.
Этап 2: Рефакторинг Бэкенда на Service Layer и Django NinjaВынести бизнес-логику из logistics/views.py и logistics/forms.py в logistics/services.py и logistics/selectors.py.   Установить django-ninja и django-ninja-jwt.Написать schemas.py и api.py для accounts (JWT логин, регистрация, профиль, сброс пароля) и logistics (CRUD заказов, смена статусов, календарь заказов, транспорт, клиенты, финансы).   Адаптировать интеграционные тесты (test_views_integration.py, test_data_isolation.py) под Ninja TestClient.
Этап 3: Реализация модулей Монетизации и Киллер-фич для продажСоздать приложения billing (Freemium-лимиты в БД и Redis) и marketplace (контекстные B2B-офферы).Добавить эндпоинт генерации печатных документов (GET /api/logistics/orders/{id}/document/docx) для автоматического заполнения Договор-заявки и ТТН по данным заказа, клиента, водителя и ТС.Написать management-команду python manage.py seed_demo_company на базе factories.py, которая наполняет демонстрационную компанию реалистичными перевозками, клиентами, машинами и финансами для презентации покупателям.
Этап 4: Разработка Frontend SPA (React)Инициализировать frontend-web (Vite + React + TypeScript + Ant Design + TanStack Query).Настроить скрипт npm run generate-api для генерации API-клиента из /api/openapi.json.Реализовать экраны: Авторизация/Регистрация, Панель диспетчера (таблица с фильтрами статусов + модальное окно Календаря), Карточка заказа (маршрут, ресурсы, блок пересчета финансов, история статусов, кнопка печати заявки и нативный блок партнерского оффера), Справочники (Клиенты, Транспорт, Водители).
Этап 5: Мобильный контур водителя и Телеметрия (IoT)Запустить легковесного Telegram-бота для водителей (получение назначенного рейса, смена статуса в 1 клик) как быстрый MVP-мост.Инициализировать mobile-driver на Flutter (авторизация водителя, список назначенных рейсов, экран активного рейса с фоновой отправкой GPS-координат).Реализовать модуль telemetry (прием координат и показаний датчиков температуры/влажности через API/WebSockets, запись истории и генерация алертов при выходе температуры рефрижератора за пределы нормы).
7. Протокол самопроверки для ИИ-агента (Definition of Done)Перед тем как завершить любую задачу и отчитаться пользователю, ИИ-агент обязан:Проверить отсутствие бизнес-логики в api.py и наличие фильтра .filter(company=...) во всех запросах.   Запустить в терминале pytest и убедиться, что все тесты (включая новые тесты на добавленный функционал) проходят успешно (0 failed).   При изменении схем schemas.py или api.py на бэкенде — обновить сгенерированный клиент во frontend-web.
