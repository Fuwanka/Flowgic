# Архитектура после этапа 1

## Существующий продукт

Изучены дерево исходников и индекс Git, конфигурация, URL, модели, формы,
представления, миграции, фикстуры/фабрики и состав всех тестовых модулей.
Прослежены шаблоны и JS ключевых сценариев: вход, панели по ролям, создание
и карточка заказа, финансы, клиенты, календарь. Изображения и каждую строку CSS
для инфраструктурного переноса анализировать не требовалось.

- `accounts.User` наследует AbstractUser, использует уникальный email вместо
  username, роли dispatcher/manager/driver, статус и тему. Компания связана
  nullable FK; восстановление пароля использует временный шестизначный код.
- `logistics.Company` — организация с UUID и JSON-адресом. Компания пока
  принадлежит logistics; её перенос в accounts относится к дальнейшей архитектуре.
- Client и Vehicle имеют прямой FK на компанию. У Vehicle номер уникален внутри
  компании. У Order компания определяется через `client.company`; поля company
  в существующей таблице orders нет. created_by может быть NULL и не является
  надёжной границей tenant.
- Order связывает клиента, создателя, водителя и ТС, хранит груз, маршрут,
  сроки и статус. Геометрия маршрута пока TextField: включение PostGIS не
  меняет тип и смысл существующих данных.
- Financial связан с заказом 1:1. Существующая формула save():
  `client_cost - fuel_expenses - driver_cost`. Автоматическое топливо вычисляется
  только при явном `fuel_expenses=None`; 0 остаётся явным нулевым расходом.
  third_party_cost пока не участвует в формуле, несмотря на старый help_text.
  Этап 1 сохраняет эту доменную логику.
- OrderEvent хранит JSON истории; Document — метаданные документов.
- Запрос проходит через Django URLs → views → ModelForm/ORM → templates.
  Бизнес-логика пока остаётся в старых views/models; полное разделение на
  services/selectors и Django Ninja относится к этапу 2.

## Инфраструктура

`src/` перенесён в `backend/`, включая миграции, шаблоны, static и тесты.
Канонические зависимости разделены на runtime и dev. Окружение — Python 3.11
и Django 5.2.18 (эта версия уже использовалась локальным venv).

Compose содержит PostGIS 16-3.4, Redis 7, миграционный процесс, backend и Celery.
Отдельный профиль test собирает образ с pytest/Playwright/Chromium. Healthcheck
БД и Redis и успешное завершение миграций определяют порядок запуска.
Runtime-контейнеры работают от пользователя app, а приложение — от PostgreSQL-роли
без SUPERUSER/CREATEDB. Тестовая роль имеет только CREATEDB дополнительно.
PostGIS в template1 позволяет создавать пространственные тестовые БД без
выдачи SUPERUSER приложению или pytest.

Настройки загружаются из корневого `.env` без переопределения переменных процесса.
Backend всегда выбирает PostGIS: запасного пути на SQLite нет. Redis используется
как Django cache; Celery broker/result используют отдельные логические БД Redis.
Встроенные почтовые реквизиты удалены; console email backend — локальное значение
по умолчанию.

Удалены генерируемые Python/pytest-кэши и большой устаревший project_structure.txt.
Исторический `src/plan` сохранён как `docs/legacy-plan.md`. Виртуальное окружение
не удалено: это рабочая локальная зависимость, исключённая из Git/индексации.
Мусорные файлы уже не отслеживались Git до начала работ, поэтому удалять их
из индекса повторно не требовалось. SQLite скопирована в исключённую папку
`.local/backups/`; совпадение SHA-256 копии проверено до удаления оригинала.
Автоматического переноса данных из SQLite в PostgreSQL на этом этапе нет.

## Выявленные исходные дефекты и необходимые исправления

До переноса небраузерный прогон на SQLite дал **86 passed, 19 failed**;
первоначальная полная сборка тестов также обнаружила отсутствие Playwright.

- Тесты обращались к отсутствующим URL `/dispatcher/`, `/driver/`, `/manager/`,
  `/logistics/new-request/` и другим. Теперь используются реальные маршруты
  существующего интерфейса и контекст `requests`; проверки не удалены.
- OrderFactory не поддерживала используемый тестами `client__company`.
  Исправлена фабрика; сами модели не изменены.
- Тест автоматического топлива передавал не тот входной контракт. Теперь он явно
  задаёт None, сохраняя прежние проверки суммы топлива и прибыли и логику модели.
- Карточка чужого заказа была доступна и создавала Financial при GET.
  Добавлен tenant-scoped selector, используемый до чтения/изменения заказа;
  водитель ограничен назначенными заказами. Lookup справочников ограничен компанией.
- Формы создания/назначения могли предлагать ресурсы чужой компании.
  Queryset полей ограничен компанией; роль водителя не может создавать заказы.
- Календарь читал все компании и ссылался на отсутствующий шаблон. Он использует
  доступные пользователю заказы и существующий calendar_modal.html.
- Браузерный тест заказа использовал старое поле username, отсутствующий URL,
  неполные обязательные данные и старый текст успеха. Сценарий приведён к текущей форме,
  помечен browser и проверяет переход в карточку, отображение груза и создание записи в БД.
- В списке клиентов отсутствовала ожидаемая тестами кнопка создания клиента.
  Добавлена ссылка для dispatcher/manager; тест открытия карточки использует
  существующую ссылку «Открыть». Права рабочей папки Docker исправлены, чтобы
  pytest мог писать свой кэш от обычного пользователя app.

Добавлены отдельные регрессии границ компаний и интеграционные проверки настоящих
PostGIS/Redis. CI запускает полную suite с миграциями, без маскировки ошибок
через `continue-on-error` или исключение slow/browser.

## Граница следующего этапа

REST/JWT, новый frontend/mobile, billing, marketplace и telemetry здесь не создаются.
Перед этапом 2 необходимо последовательно вынести старую бизнес-логику, усилить
проверки ролей всех endpoint и регистрацию компаний, сохранив формулу финансов
до отдельного согласованного изменения. Поле User.company пока допускает NULL;
новый selector в этом случае не возвращает заказы.
